## Building locally

Follows [Flathub's submission guide](https://docs.flathub.org/docs/for-app-authors/submission):
the build uses Flathub's own builder (`org.flatpak.Builder`, `flathub-build`).

```sh
just flatpak-setup  # once: org.flatpak.Builder + the user Flathub remote
just flatpak        # regenerates cargo-sources.json, builds, installs for your user
just flatpak-run    # flatpak run io.github.lemonxah.ZestBay
just flatpak-lint   # Flathub's linter on the manifest and the built repo
just flatpak-copy ../flatpak/flathub/   # copy the submission files into a folder
just flatpak-bundle # single-file dist/ZestBay-<version>.flatpak for GitHub releases
```

`flatpak-bundle` packs the local build into one file for distribution outside
Flathub (e.g. attached to a GitHub release). Users install it with
`flatpak install --user ZestBay-<version>.flatpak`; it points at Flathub for
the KDE runtime, which is fetched automatically. Bundles don't update
themselves: users install the next release's bundle.

`flatpak-copy` copies exactly what Flathub's
[required files](https://docs.flathub.org/docs/for-app-authors/requirements#required-files)
list asks for in a submission: the manifest and the generated
`cargo-sources.json` (plus `flathub.json`, if one is added to restrict
architectures). Metainfo, desktop file and icons stay upstream. It only copies
files; it does not touch git or Flathub.

`cargo-sources.json` must be regenerated (`just flatpak-sources`) whenever
`Cargo.lock` changes, because the Flatpak build has no network access.

The manifest builds from the working tree (`type: dir`, the repo root). The
sandboxed `flathub-build` only accepts directory sources inside the
manifest's directory, which is why the manifest sits at the repo root.

## Sandbox notes

- **PipeWire**: `--filesystem=xdg-run/pipewire-0` gives access to the whole
  graph, as other patchbays on Flathub do.
- **Network** (`--share=network`) is for hosted plugins, not ZestBay itself:
  licensed plugins such as Pianoteq bind their activation to the machine's
  network hardware, which a sandbox without network access can't see (they
  then show as not activated), and many plugins activate or refresh licences
  online.
- **Plugin editors** are X11 windows, so the app has the full X11 socket next
  to Wayland. The linter warns `finish-args-contains-both-x11-and-wayland`;
  that is intentional and needs explaining in the submission.
- **Plugins** are searched in `~/.lv2`, `~/.clap`, `~/.vst3`,
  `$LV2_PATH`/`$CLAP_PATH`/`$VST3_PATH`, `/app/extensions/Plugins/{lv2,clap,vst3}`
  (Flatpak plugin extensions) and the host's `/usr/lib*/{lv2,clap,vst3}` via
  `/run/host/usr` (`--filesystem=host-os:ro`). Host plugins built against
  distro libraries may fail to load in the runtime; the sandbox probe keeps
  that from crashing ZestBay. Flathub reviewers may ask about `host-os` and
  `home`; both exist so plugins and their data can be found.
- **LV2 UIs**: suil is built with the GTK 3 and X11 wrappers only, so Qt5,
  GTK2 and GTK4 LV2 UIs are not available in the Flatpak.
- **Config** lives in `~/.var/app/io.github.lemonxah.ZestBay/config/zestbay`,
  separate from a native install's `~/.config/zestbay`. Copy it over to keep
  your rules, layout and plugins.

## Submitting to Flathub

Flathub's policy: submitted manifests must not contain AI-generated or
AI-assisted content, AI tools must not open or automate the submission PR,
and AI involvement in the app must be disclosed. Parts of this repository's
packaging were AI-assisted, so the Flathub manifest has to be written by the
maintainer (this one is for local builds and testing).

- The Flathub manifest uses the release tarball
  (`https://github.com/lemonxah/zestbay/archive/refs/tags/vX.Y.Z.tar.gz` and
  its sha256) instead of the working tree, plus `cargo-sources.json`.
- Screenshots in the metainfo point at `docs/screenshots/*.png` on the
  `main` branch; regenerate them with `design/screenshots/render.sh` after UI
  changes and push before submitting.
- Add a `<release>` entry for the version being published.
- Explain every permission in the PR (see Sandbox notes).
